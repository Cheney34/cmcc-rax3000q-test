# 路线对比与选型：官方兼容 vs 完整 NSS

## 0. 一句话结论（已按实际使用场景定稿）

**主推只走轨道 A：官方主线 + 最新内核 + `apk` 官方包源。**

「完整高通 NSS」需要 QSDK 5.4 老内核（轨道 B），它与官方主线在**内核层**互斥；
但**如果你的线路在千兆以内（例如校园网），NSS 没有实际收益** —— 官方主线的软件 flow offloading 就能跑满线路，
换来的是「新内核 + 官方长期维护 + 完整包生态」。所以**本仓库默认不启用 NSS**，轨道 B 只作为可选实验保留。
两条产物可互刷、可来回切。

### 0.1 什么时候才值得折腾 NSS

| 场景 | 建议 |
|---|---|
| 千兆以内（校园网/家宽 500M~1G） | **不用 NSS**，轨道 A 软件转发足够，跑满线路 |
| 2000M 以上线路，或要做几十条 NAT + 大流量（PT/多播/多拨） | 才考虑轨道 B 或其它 NSS 方案 |
| 只想「CPU 占用低一点」 | 收益有限，不如直接用轨道 A |

补一句技术事实：IPQ5018 **没有 PPE 块**（PPE 是 ipq807x/ipq60xx 的硬件），
它唯一的卸载引擎就是 NSS 的 UBI32 核；而官方 OpenWrt **没有把 NSS offload 栈合进主线**
（相关 PR #13560 / #14172 都被 close），mainline 上也没有可替代的硬件卸载路径。
所以「官方内核 + 官方源 + 硬件卸载」这个组合在 IPQ5018 上目前**不存在**，只能二选一。

## 1. 为什么不能一条路走通

### 1.1 包格式：官方已经不是 `.ipk` 了

| 发行版 | 包管理器 | 后缀 |
|---|---|---|
| OpenWrt 24.10 及更早 | `opkg` | `.ipk` |
| **OpenWrt 25.12 / snapshot** | **`apk`**（Alpine 的 apk-tools） | **`.apk`** |

证据：官方 snapshot `qualcommax/ipq50xx` 的 `profiles.json` 里，`default_packages` 含 **`apk-mbedtls`**，且**不含 `opkg`**。

所以「装官方任何支持该架构的 ipk」这句话本身需要更新为：
- 在 25.12/snapshot 上 → `apk add <包名>`，包来自官方 `packages` 源（轨道 A）。
- 想要真正的 `.ipk` + `opkg` → 只能用 21.02 时代的老树（轨道 B），但那是 ImmortalWrt 源，不是官方源。

### 1.2 内核 kmod 的硬约束（最容易被忽略的一条）

官方 kmod 包（`kmod-*`）在自己元数据里记录了**内核 vermagic**。snapshot 上 RAX3000Q 的 vermagic 是：

```
d32d64835c74cf3585b84878ae80a0a6     (kernel 6.18.55)
```

只要你在编译时改动内核配置（哪怕只加一个模块），这个哈希就变，**官方源里的 `kmod-*` 全部装不上**（报 `unable to satisfy dependency` / `kernel hash mismatch`）。

因此轨道 A 采取了**不编译 kmod 的迂回策略**（见 §3.1）：内核用官方源码、官方配置**原封不动**地编，kmod 包一律从官方源二进制安装。这样 `kernel` 与官方 snapshot 二进制等价，官方 kmod 可用。

**纯用户态包**（`luci-*`、`opennds`、`curl`、`python3`…）不受此限制，任何路线都能装。

### 1.3 NSS 的现状

`ipq50xx` 是 ipq5018 平台。高通 NSS（Network Subsystem）的完整加速需要三件套：

| 组件 | 作用 |
|---|---|
| `kmod-qca-nss-dp` | NSS-DP 数据面以太网驱动 |
| `kmod-qca-nss-drv` | NSS 固件加载与 NSS 核心驱动 |
| `qca-nss-fw-ipq50xx-retail` | NSS 固件二进制 |
| （NAT 卸载还需 ECM/`qca-nss-ecm`）| 连接管理器，把 NAT/conntrack 卸载到 NPU |

在 kkstone 那条线上，`target/linux/ipq50xx/Makefile` 的 `DEFAULT_PACKAGES` 里直接写着：

```make
DEFAULT_PACKAGES += \
	kmod-gpio-button-hotplug \
	uboot-envtools \
	kmod-qca-nss-dp swconfig \
	kmod-qca-nss-drv qca-nss-fw-ipq50xx-retail \
	kmod-ath11k wpad-basic-wolfssl
```

即 **NSS 是那个 target 的默认项**，只要编就一定带上 —— 这就是轨道 B 存在的全部价值。

### 1.4 官方两条分支的实测差异（决定了「官方 + NSS」不可能）

| | `openwrt-25.12`（内核 6.12.94） | `main`（内核 6.18，= snapshot） |
|---|---|---|
| 有没有 `cmcc_rax3000q` 设备 | ❌ **没有**（只有 pz-l8 / mr3000d-ci / gl-b3000 等 13 个设备）| ✅ **有**（commit `d592680cc501cd7decdffb50b80c964d128c22ef`）|
| 以太网驱动 | 外置 `kmod-qca-nss-dp` + `kmod-qca-ssdk`，且写在 target `DEFAULT_PACKAGES` 里（默认带上）| **换成内核自带 mainline stmmac**（`CONFIG_DWMAC_IPQ5018=y` / `CONFIG_STMMAC_ETH=y`），`kmod-qca-nss-dp` 已从 main 删除 |
| 真正的 NSS 卸载（NSS-DRV + ECM）| ❌ 官方从未合并（PR #13560 / #14172 被 close）| ❌ 同左 |
| 包格式 | `.apk`（无 `opkg`）| `.apk` |

结论：**官方唯一带 NSS 相关代码的分支（25.12）没有这台设备；而支持这台设备的分支（main）已经把 NSS-DP 换成了主线 stmmac。**
所以「官方内核 + 官方源 + NSS 硬件卸载」在 IPQ5018 上**不存在**，只能二选一；
你的线路在千兆以内，选**官方主线**即可（软件转发足够，且内核最新）。

## 2. 轨道 B（完整 NSS）细节与代价

- 源码：`kkstone/immortalwrt-ipq50xx`，分支 `openwrt-21.02`（该仓库**只有这一个分支**，fork 自 `immortalwrt/immortalwrt`，`pushed_at` 停在 **2024-09-17**）。
- `feeds.conf.default` 只有 4 个源，全部锁 `openwrt-21.02`：`immortalwrt/packages`、`immortalwrt/luci`、`openwrt/routing`、`openwrt/telephony`。
- 代价：
  1. 21.02 已停止维护（安全更新没有了）。
  2. 装不了官方 OpenWrt 的包（ABI 与 feed 都不同）。
  3. 原仓库 `.config` 有 **280 KB**（大量可选包），本仓库**不继承**它，改为从 `make defconfig` 生成**精简**配置，只显式勾选需要的包。

## 3. 轨道 A（官方兼容）细节

### 3.1 怎么做到「官方内核 + 能装官方包」

纯用户态包（LuCI、portal、IPv6 工具）**编译进固件**，内核配置**一行都不加**：

1. `git clone https://github.com/openwrt/openwrt`，默认 `checkout` **main 最新 HEAD**（= 官方在用的最新内核）；
   工作流的 `ref` 输入可以固定任意提交，例如 `ae9276426c2e51ebba1732f952b0592ca8af24b6`（= 官方 snapshot `r37117-ae9276426c`，与官方产物同源）。
2. `./scripts/diffconfig.sh` 之类的「全量对比」**不使用**；配置里只勾 target/device 与用户态包。
3. 工作流有一条**硬性检查**：`.config` 里只要出现 `CONFIG_PACKAGE_kmod-*=y` 就直接 `::error::` 退出
   （内核模块必须由官方源提供，自己选 kmod 会改内核配置 → 改 vermagic）。
4. 构建后再把本地产物的 `.vermagic` 与官方 `profiles.json` 对比，并写进 artifact（`vermagic-compare.txt`）。

**什么时候官方 `kmod-*` 也能装？** 只有 `ref` 与官方快照提交完全一致时（内核配置与内核版本都相同 → vermagic 相同）。
默认跟 main HEAD 走时内核更新，vermagic 必然不同，**官方 `kmod-*` 装不上，但用户态包照装**（这是 `.vermagic` 机制决定的，见 §1.2）。
日常使用（LuCI、portal、IPv6、常用工具）全是用户态包，不受影响；真有必需的内核模块，就在 `ref` 对齐的那次构建里用，或改用轨道 B。

### 3.1.1 安装包的正确姿势

```
apk update
apk add luci-app-xxx kmod-usb-storage        # 用户态包永远可用；kmod 取决于 ref 是否对齐官方快照
```

### 3.2 Wi-Fi 固件必须补（官方 profile 的坑）

官方 snapshot 的 `cmcc_rax3000q` profile 里 **`device_packages` 是空的 `[]`**，
也就是**默认不装 ath11k 固件、也不装板级 BDF**（对比 `cmcc_mr3000d-ci` 就有 `ath11k-firmware-ipq5018-qcn6122` 和 `ipq-wifi-cmcc_mr3000d-ci`）。
轨道 A 的配置显式补上无线固件与板级数据，否则刷完**没有 Wi-Fi**。

### 3.3 官方支持的可用性

- ❌ 官方 **25.12.5 正式版**的设备列表里**没有** `cmcc_rax3000q`。
- ✅ 官方 **snapshot/main** 里有（`supported_devices: ["cmcc,rax3000q"]`）。
- 官方 snapshot 的 `file_size_limits.image` = **60817408 B（58 MiB）**，本仓库的镜像远小于该上限。

所以轨道 A 用的是 **snapshot 语义**（同内核、同 vermagic、同包源），而不是某个固定 release。
这是「能装官方包」这条需求目前**唯一可行**的实现方式。

## 4. 决策建议（按你的实际场景：校园网 / 千兆以内 / 要新内核）

| 你的优先级 | 选 |
|---|---|
| 新一点的官方内核、长期维护、能装官方包、IPv6、portal、改 MAC | **轨道 A**（默认，只跑这个就够） |
| 千兆以内的线路（校园网、500M~1G 家宽） | **轨道 A**：软件 flow offloading 足够跑满，NSS 没有收益 |
| 2000M 以上线路，或要靠卸载把 CPU 压下来 | 轨道 B（代价：内核 5.4、21.02 已停更、装不了官方源包） |
| 想要 `.ipk` 文件、习惯 `opkg install` | 轨道 B（注意：ImmortalWrt 源，不是官方源） |
| 不确定 | 先刷 **轨道 A**；想试 NSS 再用 U-Boot 网页刷 **轨道 B**，随时能刷回来 |
